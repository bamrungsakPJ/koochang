# C01 decisions — bank-transfer payments and the platform identity they need (2026-10-04)

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Channel | Bank transfer only. The invoice shows bank, account name, number, optional PromptPay ID and the invoice number as reference. Without `PAYMENT_*` settings owners cannot create invoices (503); no account is hard-coded. | Commercial §5. The real receiving account is a business decision for the team. |
| 2 | Invoice | Owner picks a paid plan; the invoice freezes plan and price snapshots and a number `INV-YYMM-nnnnnn`. One open invoice per shop; picking another plan voids the open one as `replaced` unless a proof is being checked. Same `request_key` → same invoice. A plan with fewer seats than the active technicians is refused (`SEAT_LIMIT_REACHED`). | Price changes never touch issued invoices; downgrade rule in Commercial §4. |
| 3 | Proof | Image bytes to `PUT …/invoices/:id/proof?proof_id=`; re-encoded with metadata removed, stored privately under `billing/…`, not counted in the shop's photo quota (an expired shop must still be able to pay). A proof changes nothing about the entitlement. | Commercial §5: a slip is not proof of payment. |
| 4 | Confirmation | A billing operator confirms money received from the bank statement: amount, bank reference (normalized: upper case, no spaces, unique across all payments) and received time. Same reference + same invoice → the earlier result (`existing`); same reference on another invoice → `BANK_REFERENCE_USED`; wrong amount → `PAYMENT_AMOUNT_MISMATCH`, audited, entitlement unchanged (exception queue). Payment, invoice paid, proof accepted, paid period (`billing.apply_paid_period`, confirmation time = now), audit and owner notification happen in one transaction. | Commercial §4–5, CLAUDE.md rule 10. The A03 period rules decide where the period starts (from the end of the previous paid period during grace, otherwise at confirmation). |
| 5 | Refunds | Request (operator, `refund.request`) → approve/reject (`refund.approve`, never the requester: checked in the function and by the table constraint) → succeeded with a unique bank reference, or failed. The total of pending/approved/succeeded refunds never exceeds the payment (row lock). A refund never changes the entitlement. | Commercial §5. |
| 6 | Platform identity | Separate accounts (`platform.accounts`) and sessions (`platform.sessions`, token hashes). Sign-in = email + scrypt password + TOTP (RFC 6238, ±1 step, a used step is rejected). Five failures lock the account 15 minutes. Every failure answers `LOGIN_FAILED`. Session 12 h. Money/access actions need a TOTP step-up within 10 minutes (`STEP_UP_REQUIRED`). Accounts are created/reset/disabled with `scripts/platform-account.mjs` by the server operator (audited); no sign-up, no root account in the app. | Functional §23, DB §18.1–18.2. |
| 7 | Least privilege | Role `fs_platform` (no superuser, no BYPASSRLS) can only execute `padmin.*` functions; it cannot select any table. Each function calls `padmin.require(account, permission)`; the API checks the same permission first. `fs_api` cannot reach `padmin`. Seven roles map to permissions (`billing.verify`, `refund.request`, `refund.approve`, …). | CLAUDE.md rule 2; least privilege per command. |
| 8 | Platform audit | `platform.audit_logs` is append-only (trigger blocks UPDATE/DELETE/TRUNCATE for everyone). Proof views, confirmations, mismatches, rejections and each refund step are recorded with actor, permission, target and request id. | DB §18.2. |
| 9 | Reconciliation | `GET /platform/billing/reconciliation.csv?from&to`: payments and succeeded refunds (negative) by Bangkok day, UTF-8 BOM, spreadsheet-formula-safe cells. | Commercial §8. |
| 10 | Console | `apps/admin` `/console`: sign-in + MFA, payment queue (proofs to check / unpaid / paid), invoice detail with the proof image, confirm or reject, refunds with approve/transfer, reconciliation download. Token in sessionStorage. th/en catalog `adminText`. | Functional §23. |

Prices stay the seed's proposal values (Starter 590, Team 1,290 THB) and are labelled as pilot prices in the app.

Not in C01: receipts/tax documents (company document type not chosen), automatic slip reading, payment gateways, scheduled plan changes at period end, editing plan/price versions in the console, approval workflow for granting high roles (accounts are managed by the operator script for now).
