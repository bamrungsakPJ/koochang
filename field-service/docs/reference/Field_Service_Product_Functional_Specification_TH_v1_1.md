### วัตถุประสงค์ของเอกสาร

กำหนดพฤติกรรมของระบบตั้งแต่รับงานจนถึงสร้างนัดบริการครั้งถัดไป เพื่อให้ร้านตอบได้ว่าลูกค้าคนไหน มีอุปกรณ์อะไร เคยทำอะไร และต้องกลับไปดูแลเมื่อไร ข้อมูลจากงานจริงต้องนำกลับมาใช้ได้โดยไม่บังคับกรอกซ้ำ และการใช้งานของช่างต้องรวดเร็วบนมือถือ

ข้อกำหนดหลักในเอกสารใช้เป็น baseline ของ MVP รวม Subscription และ Platform Administration ตามหัวข้อ 21 ถึง 25 รายละเอียดที่ระบุว่า “ข้อเสนอเพื่อพัฒนา” หรือ “ต้องตัดสินใจก่อนพัฒนา” เป็นแนวทางประกอบที่ต้องตกลงเพิ่มเติม ส่วนโครงสร้างข้อมูลเป็นระดับแนวคิดและยังต้องแตกเป็น schema และ API contract

### กติกาหลักที่ต้องรักษา

• Installation เป็น optional อุปกรณ์เริ่มประวัติจากบริการประเภทใดก็ได้

• QR sticker ประจำอุปกรณ์ไม่บังคับ และไม่ต้องพกเครื่องพิมพ์

• AI Assists, Never Blocks ถ่ายแล้วไปต่อได้ แม้ OCR ล้มเหลว

• เก็บเฉพาะพิกัดสถานที่ลูกค้าเมื่อผู้ใช้กดบันทึก ไม่มีการติดตามช่าง

• Capture Once, Reuse Forever เก็บข้อมูลแล้วใช้ต่อในงานถัดไป

• Don’t Become ERP จำกัดการพัฒนาไว้ที่วงจรงานบริการ

## 1 พันธกิจและขอบเขตผลิตภัณฑ์

ช่วยให้ร้านและทีมช่างบันทึกงานบริการอย่างง่าย สะสมความรู้เกี่ยวกับลูกค้าและอุปกรณ์ และเปลี่ยนรอบดูแลที่ถึงกำหนดเป็นงานบริการครั้งใหม่ โดยไม่ต้องพึ่งความจำของช่างคนเดิมหรือค้นหารูปในแชต

ผู้ใช้หลักคือ Owner และ Technician บน iOS และ Android ลูกค้าไม่ต้องติดตั้งแอป กลุ่มทดลองแรกคือร้านแอร์ แต่แบบจำลองข้อมูลต้องรองรับเครื่องกรองน้ำ CCTV Solar ปั๊มน้ำ เครื่องจักร EV Charger และอุปกรณ์ประเภทอื่น โดยไม่ผูกชื่อ field หรือ logic กับแอร์

วงจรหลักคือ รับการติดต่อ → ค้นหาหรือสร้างลูกค้า → เลือกสถานที่ → สร้างนัดและมอบหมาย → ช่างบันทึกบริการจริง → ประวัติรายเครื่อง → ตั้งรอบดูแล → แจ้ง Owner → ติดต่อลูกค้า → นัดและมอบหมายรอบใหม่

ระบบรองรับร้านที่มีช่างหลายคน ไม่จำกัดแนวคิดเฉพาะร้านเล็ก การเพิ่มช่างต้องไม่เพิ่มภาระการสมัครหรือการเชิญรายบุคคล ขนาดทีมที่ใช้ทดสอบและความจุระบบต้องกำหนดในแผนเปิดใช้งาน

## 3 องค์กรและสิทธิ์ผู้ใช้

### 3.1 ขอบเขตองค์กร

หนึ่งร้านเท่ากับหนึ่ง Organization ข้อมูลธุรกิจทั้งหมดต้องอยู่ในขอบเขตร้านนั้น User เชื่อมร้านผ่าน OrganizationMember ซึ่งมี role และสถานะสมาชิก การมีลิงก์ร้านไม่ให้สิทธิ์เข้าถึงข้อมูลร้าน

| ความสามารถ | Owner | Technician |
| --- | --- | --- |
| ตั้งค่าร้านและจัดการสมาชิก | ได้ | ไม่ได้ |
| อนุมัติ ปฏิเสธ ระงับ หรือนำช่างออก | ได้ | ไม่ได้ |
| สร้าง นัด มอบหมาย เปลี่ยนวันและยกเลิกงาน | ทุกงานในร้าน | งานหน้างานตามสิทธิ์ |
| ดูงาน | ทุกงานในร้าน | งานที่ตนได้รับมอบหมาย |
| ลูกค้า สถานที่ อุปกรณ์และประวัติ | ทั้งร้าน | ที่จำเป็นต่อการทำงานและค้นหาตามสิทธิ์ |
| เพิ่มอุปกรณ์และบันทึกพิกัดสถานที่ | ได้ | ได้ในบริบทงานที่มีสิทธิ์ |
| บันทึกบริการ รูปและปิดงาน | ดูและจัดการตามนโยบาย | งานของตนและงานที่สร้างหน้างาน |
| ดูรายการถึงรอบและสร้างนัดใหม่ | ได้ | กำหนดรอบของอุปกรณ์ที่ทำบริการ |

MVP มีเพียง Owner และ Technician ไม่เพิ่ม role ผู้จัดการ หัวหน้าช่าง ฝ่ายขาย หรือสิทธิ์แบบซับซ้อน ต้องตัดสินใจขอบเขตการค้นหาลูกค้าทั้งร้านของช่างก่อนพัฒนา โดยใช้สิทธิ์น้อยที่สุดที่ยังทำงานหน้างานได้

### 3.2 สถานะสมาชิก

คำขอเข้าร่วมอยู่ใน pending จน Owner อนุมัติ สมาชิก active จึงรับงานและใช้ข้อมูลได้ suspended และ removed ต้องถูกปฏิเสธโดย backend แม้ยังมี session ในมือถือ การนำสมาชิกออกต้องไม่ลบชื่อผู้บันทึกในประวัติเดิม

## 4 การสมัครร้านและการเข้าร่วมทีม

### 4.1 Owner registration

หน้าเริ่มต้นมี สร้างร้าน และ เข้าสู่ระบบ ข้อมูลขั้นต่ำคือชื่อร้านและเบอร์โทร ชื่อผู้ใช้งานและอีเมลเป็นข้อมูลเพิ่มเติม เมื่อสมัครสำเร็จสร้าง User Organization และ OrganizationMember role owner เป็นชุดเดียวกัน ไม่ให้เกิดร้านที่ไม่มี Owner

ข้อเสนอเพื่อพัฒนา ยืนยันตัวตนผ่านเบอร์โทรและ OTP และรักษา session อย่างปลอดภัย วิธี login และการกู้บัญชีต้องเลือกก่อนพัฒนา ไม่ผูกการใช้งานหลักกับ LINE Login

### 4.2 Join Link และ QR ของร้าน

ร้านมี reusable Join Link และ Join QR หนึ่งชุดที่ใช้ได้กับช่างทุกคน Owner แชร์เข้า LINE กลุ่มหรือส่งด้วยตนเองได้ QR นี้ใช้เข้าร่วมร้านและเป็นคนละกรณีกับ QR sticker ของอุปกรณ์ ห้ามนำสอง flow มาปะปนกัน

ช่างเปิดลิงก์หรือสแกน QR เห็นชื่อร้าน ใส่ชื่อที่ใช้ในร้าน และกด ขอเข้าร่วม หากยังไม่มีแอปต้องกลับเข้าหน้าร้านเดิมหลังติดตั้งได้ Owner ได้คำขอพร้อมปุ่ม อนุมัติ และ ปฏิเสธ เมื่ออนุมัติจึงเปิดใช้งานเป็น Technician

ไม่บังคับช่างกรอกอีเมล รหัสผ่าน ข้อมูลบริษัท หรือข้อมูลส่วนตัวหลายช่อง เป้าหมายคือส่งคำขอได้ใน 10–20 วินาที โดยแยกเวลารอ Owner อนุมัติออกจากเวลาการสมัคร

### 4.3 การควบคุมและข้อผิดพลาด

• Owner ปิดการเข้าร่วมและ reset ลิงก์ได้ ลิงก์เก่าต้องส่งคำขอใหม่ไม่ได้หลัง reset

• ลิงก์ที่ปิดหรือใช้ไม่ได้แสดงข้อความเข้าใจง่าย ไม่เปิดข้อมูลภายในร้าน

• คำขอซ้ำต้องไม่สร้างสมาชิกซ้ำ สมาชิก active ที่เปิดลิงก์เดิมเข้าสู่ร้านได้

• ระหว่าง pending หรือ rejected ห้ามอ่านข้อมูลลูกค้าและงาน

• เก็บ session เพื่อเปิดแอปครั้งต่อไปได้ การเปลี่ยนเครื่องและกู้บัญชีต้องมีวิธียืนยันตัวตนที่ตกลงไว้

## 5 ลูกค้าและสถานที่ให้บริการ

### 5.1 Customer

Customer เก็บชื่อ เบอร์โทร และหมายเหตุ โดยเบอร์โทรเป็นจุดค้นหาหลัก Owner สร้างจากหน้ารับงานได้ทันที ช่างใช้ flow งานหน้างานที่สร้างข้อมูลเบื้องหลัง ไม่ต้องไปกรอกหลายหน้าก่อนเริ่มบันทึก

ข้อเสนอเพื่อพัฒนา กำหนดเบอร์โทรเป็นข้อมูลขั้นต่ำในการติดต่อลูกค้า ชื่อสามารถกรอกภายหลังใน flow หน้างานได้ และแสดงชื่อชั่วคราวจากเบอร์โดยไม่แต่งชื่อบุคคล กรณีลูกค้ามีเบอร์กลางร่วมกันต้องให้เลือกหรือสร้างแยกด้วยเหตุผล ไม่ merge อัตโนมัติ

### 5.2 CustomerLocation

Customer และ CustomerLocation เป็นคนละ entity ลูกค้าหนึ่งรายมีหลายสถานที่ได้ เช่น บ้าน ร้าน โกดัง หรือหลายสาขา งานหนึ่งเลือกสถานที่ให้บริการหนึ่งแห่ง และอุปกรณ์แต่ละรายการอยู่ใต้สถานที่นั้น

| ข้อมูล | ข้อกำหนด |
| --- | --- |
| customer_id และ organization_id | ต้องมีและอยู่ร้านเดียวกัน |
| ชื่อสถานที่ | เช่น บ้าน โกดัง สำนักงาน |
| ที่อยู่และหมายเหตุการเดินทาง | เก็บคำอธิบายที่ช่วยไปถึงได้ แม้ไม่มีพิกัด |
| latitude และ longitude | optional ต้องมีเป็นคู่เมื่อบันทึกพิกัด |
| accuracy | ความแม่นยำจากการอ่าน GPS ถ้ามี |
| location_captured_at และ location_captured_by | เวลาและผู้บันทึกพิกัดสถานที่ |
| แหล่งพิกัด | ข้อเสนอ เก็บว่าอ่าน GPS หรือปักด้วยตนเอง |

Owner สร้างงานได้แม้ยังไม่มีพิกัดและยังไม่ทราบอุปกรณ์ ช่างเพิ่มเติมข้อมูลเมื่อถึงสถานที่จริง การแก้พิกัดเดิมต้องเป็นการกระทำโดยตั้งใจพร้อมยืนยัน ไม่เขียนทับอัตโนมัติทุกครั้งที่เข้าให้บริการ

## 6 นโยบาย GPS และการนำทาง

ข้อกำหนดตายตัว ระบบเก็บเฉพาะพิกัดของสถานที่ลูกค้า ไม่ติดตามช่าง ไม่มี background GPS ไม่มี live location ไม่มีเส้นทางย้อนหลัง และไม่มี GPS ตอนเริ่มงานหรือเสร็จงาน ServiceEvent และ Job ไม่ใช้พิกัดของช่างเป็นหลักฐาน

### 6.1 การบันทึกพิกัด

Owner ปักตำแหน่งสถานที่ล่วงหน้าได้ ช่างที่ถึงหน้างานกด บันทึกตำแหน่งสถานที่นี้ แล้วแอปขอสิทธิ์ While Using the App อ่านตำแหน่งเพียงครั้งเดียว แสดงผลให้ตรวจสอบและบันทึกลง CustomerLocation จากนั้นหยุดอ่าน ไม่ขอ Always หรือสิทธิ์ background

ถ้าปฏิเสธสิทธิ์ GPS ปิด หรืออ่านตำแหน่งไม่ได้ ให้ข้ามและทำงานต่อได้ ถ้าความแม่นยำต่ำให้แสดงค่าและให้เลือกลองใหม่หรือยืนยัน ไม่มีเกณฑ์ความแม่นยำที่ขวางการปิดงาน การเปิดแอป หน้า Job ปุ่มเริ่มงาน ปุ่มเสร็จงาน และการถ่ายรูปต้องไม่กระตุ้นการอ่าน GPS

### 6.2 การใช้พิกัดครั้งถัดไป

ปุ่ม นำทาง เปิด Google Maps หรือ Apple Maps ด้วย latitude และ longitude ที่บันทึกใน CustomerLocation ช่างคนใหม่ใช้พิกัดเดิมได้ ระบบไม่ต้องติดตามการเดินทางในแอปบริการ หากยังไม่มีพิกัดให้แสดงที่อยู่และตัวเลือกเปิดแผนที่ค้นหาที่อยู่ โดยระบุว่าตำแหน่งอาจไม่แม่นยำ

ข้อเสนอเพื่อพัฒนา ลบ GPS EXIF ออกจากภาพก่อนจัดเก็บหรือส่งต่อ OCR เพื่อป้องกันการเก็บตำแหน่งจากภาพโดยไม่ได้ตั้งใจ การรักษาภาพต้นฉบับหมายถึงรักษาภาพป้ายที่ใช้ตรวจข้อมูล ไม่จำเป็นต้องเก็บ metadata ตำแหน่งที่ไม่เกี่ยวข้อง

## 7 อุปกรณ์และการใช้กล้องกับ OCR

### 7.1 Equipment

Equipment เป็น entity อิสระใต้ CustomerLocation เก็บ category brand model serial_number nickname note และรูปหลายรูป รองรับชื่อเรียกเช่น แอร์ห้องนอน วันที่ติดตั้งและผู้ติดตั้งเป็น optional ไม่ต้องรู้ว่าใครขายหรือติดตั้งจึงเริ่มใช้ระบบได้

Installation เป็น ServiceEvent ประเภทหนึ่งเท่านั้น ประวัติแรกอาจเป็น repair maintenance inspection replacement หรือ other ไม่มี installation record ก็ต้องเพิ่มอุปกรณ์และปิดบริการได้

### 7.2 Camera first

เพิ่มอุปกรณ์ → ถ่ายป้ายเครื่อง → ไปต่อได้ → ถ่ายตัวเครื่อง → ระบุชื่อเรียกถ้าต้องการ OCR อ่าน Brand Model Serial เป็นข้อเสนอ ผู้ใช้ตรวจ ยอมรับ หรือแก้ไขก่อนใช้เป็นข้อมูลที่ยืนยันแล้ว สนับสนุนถ่ายต่อหลายเครื่องโดยไม่สร้างลูกค้าและสถานที่ซ้ำ

แนะนำให้มีรูปป้ายและรูปตัวเครื่องอย่างละหนึ่งรูปเมื่อทำได้ แต่ป้ายที่ซีด ไม่มีซีเรียล ถ่ายยาก หรือกล้องใช้ไม่ได้ ต้องมีช่องกรอกเองหรือข้ามได้ ไม่บังคับ Brand Model Serial ครบจึงทำงานต่อ

### 7.3 AI must never block workflow

• OCR ประมวลผลแยกจากการบันทึกธุรกิจ ไม่รอผลเพื่อเพิ่มอุปกรณ์ เริ่มงาน หรือปิดงาน

• ผลผิด อ่านไม่ได้ timeout อินเทอร์เน็ตช้า หรือ provider ล่มต้องไม่ทำข้อมูลบริการหาย

• เก็บภาพป้ายไว้เพื่อให้ตรวจและประมวลผลใหม่ได้ตามนโยบายเก็บรักษา

• ผลที่มาภายหลังต้องไม่เขียนทับค่าที่ผู้ใช้แก้หรือยืนยันแล้วโดยเงียบ ๆ

• แสดงค่าที่ไม่แน่ใจให้ตรวจ โดยเฉพาะ 0/O 1/I 5/S ไม่เดาข้อมูลที่อ่านไม่ได้

• แยก provider ผ่าน interface เพื่อเปลี่ยนผู้ให้บริการ OCR ได้ในอนาคต

### 7.4 การระบุเครื่องและข้อมูลซ้ำ

ใช้ Customer Location Photo Nickname Brand Model และ Serial ประกอบกัน ไม่ใช้ Serial เพียงอย่างเดียวเป็น identity ของทุกธุรกิจ serial อาจซ้ำข้ามยี่ห้อหรือไม่มีได้ Equipment ต้องมีรหัสภายในระบบของตนเอง

ก่อนสร้างใหม่ แสดงอุปกรณ์ที่อาจซ้ำให้ผู้ใช้เลือกของเดิมหรือยืนยันสร้างใหม่ ไม่ merge อัตโนมัติ QR sticker เป็น optional future feature ไม่มีข้อกำหนดเครื่องพิมพ์หรือขั้นตอนติดสติกเกอร์ใน MVP

## 8 การสร้างงานและมอบหมายงาน

### 8.1 Job ที่วางแผนไว้

Job คือสิ่งที่นัดหรือวางแผนว่าจะไปทำ เก็บลูกค้า สถานที่ ประเภทงาน รายละเอียดหรืออาการ วันที่ เวลา ช่างที่มอบหมาย และรายการอุปกรณ์ถ้าทราบ ข้อมูล actual service ต้องแยกไว้ใน ServiceEvent

Owner กด สร้างงาน → ค้นจากเบอร์ → เลือกหรือสร้างลูกค้า → เลือกหรือเพิ่มสถานที่ → ระบุประเภทและอาการ → เลือกวันเวลา → เลือกช่าง → สร้างและมอบหมาย ช่างได้รับแจ้งงานใหม่และเปิดรายละเอียดได้

รองรับไม่ทราบอุปกรณ์ เช่น ล้างแอร์ประมาณ 3 เครื่อง เก็บจำนวนประมาณเป็นข้อมูลวางแผน ไม่สร้างอุปกรณ์สมมติ 3 รายการก่อนช่างยืนยัน หนึ่ง Job เชื่อม Equipment ได้หลายรายการภายในสถานที่เดียวกัน

### 8.2 ตารางงานและ assignment

Owner ดูงานตามวันและช่าง รวมถึงงานรอมอบหมาย ช่างเห็นงานของตนตามลำดับนัด Owner เปลี่ยนวันเวลา ช่าง หรือยกเลิกได้ และแจ้งผู้ที่ได้รับผลกระทบ หากมอบหมายช่างใหม่ ช่างเก่าต้องไม่ยังได้รับสิทธิ์แก้ไขงานจาก assignment เก่า

ข้อเสนอเพื่อพัฒนา แสดงเตือนเวลานัดชนกัน แต่ไม่ทำ route optimization การมอบหมายหลายช่างต่อหนึ่งงานสามารถรองรับด้วย JobAssignment ในแบบจำลองข้อมูล ส่วน MVP ต้องเลือกว่าจะมีช่างหลักคนเดียวหรือทีม และกำหนดผู้มีสิทธิ์ปิดงานให้ชัด

การบันทึกงานสำเร็จไม่ขึ้นกับการส่ง push สำเร็จ งานต้องปรากฏในแอปแม้ผู้ใช้ปิดแจ้งเตือน คำขอสร้างงานซ้ำจากการกดหรือ retry ต้องไม่สร้างงานหลายรายการโดยไม่ตั้งใจ

## 9 สถานะงานและกติกาการเปลี่ยนสถานะ

| สถานะ | ความหมายและ trigger |
| --- | --- |
| unassigned | สร้างแล้ว รอมอบหมาย อาจมีวันนัดเบื้องต้น |
| scheduled | มีวันเวลาและช่างที่ active พร้อมไปทำงาน |
| in_progress | ช่างกดเริ่มงาน ไม่มีการอ่าน GPS |
| completed | บันทึกบริการจริงและกดเสร็จงาน ไม่มีการอ่าน GPS |
| cancelled | ยกเลิกแผนงาน ไม่สร้างประวัติบริการสมมติ |

เส้นทางหลัก unassigned → scheduled → in_progress → completed Owner ยกเลิกงานที่ยังไม่เสร็จได้ การเปลี่ยนช่างหรือเวลาไม่สร้างสถานะใหม่ งาน completed และ cancelled เป็นสถานะปลายทางใน MVP การเปิดใหม่ต้องกำหนดนโยบายก่อนเพิ่ม

ข้อเสนอเพื่อพัฒนา การยกเลิกหลังเริ่มงานต้องให้เหตุผลและรักษาบริการจริงที่บันทึกไว้ งาน cancelled ที่ยังไม่ได้ทำไม่มี ServiceEvent แต่ถ้าทำจริงบางส่วนแล้ว ห้ามลบหลักฐานนั้น การแก้ไข concurrent ต้องแจ้งว่าข้อมูลเปลี่ยนและให้โหลดล่าสุด ไม่เขียนทับเงียบ ๆ

เวลาเริ่มและเสร็จงานเป็น timestamp ของการดำเนินงาน ไม่ใช่ GPS check in และไม่ใช้เป็นหลักฐานติดตามตำแหน่งช่าง

## 10 การทำงานของช่างและงานเพิ่มเติม

### 10.1 งานที่ได้รับมอบหมาย

• เปิด วันนี้ เห็นชื่อ ลูกค้า เวลา ประเภทงาน จำนวนอุปกรณ์ และสถานะ

• เปิดรายละเอียด เห็นเบอร์โทร ที่อยู่ หมายเหตุเดินทาง ปุ่มโทรและนำทาง อาการและอุปกรณ์เดิม

• กดเริ่มงานเมื่อพร้อม ปุ่มนี้เปลี่ยนสถานะเท่านั้น

• บันทึกพิกัดสถานที่ด้วยปุ่มแยกเมื่อยังไม่มีและผู้ใช้ต้องการ

• เลือกเครื่องเดิมจากรูปหรือเพิ่มหลายเครื่องด้วยกล้อง

• บันทึกประเภทบริการจริง สิ่งที่พบ สิ่งที่ทำ และรูปก่อนหลังแยกรายเครื่องเมื่อจำเป็น

• ตั้งรอบดูแลแต่ละเครื่องหรือเลือกไม่เตือน ตรวจข้อมูลแล้วกดเสร็จงาน

### 10.2 หลายอุปกรณ์และผลต่างกัน

งานล้าง 3 เครื่องเลือกและบันทึกพร้อมกันได้ แต่ผลจริงอาจต่างกัน เช่น เครื่องหนึ่งล้าง เครื่องหนึ่งซ่อม และอีกเครื่องไม่ได้ทำ ต้องบันทึกเฉพาะเครื่องที่บริการจริงและระบุงานที่ไม่ได้ทำ ไม่สร้าง history ให้เครื่องที่ไม่ได้รับบริการเพียงเพราะอยู่ใน Job

### 10.3 Ad hoc jobs

ช่างกด บันทึกงาน จากหน้าแรกได้แม้ไม่มีนัดล่วงหน้า ค้นหาหรือสร้างลูกค้าและสถานที่ เลือกเครื่องหรือเพิ่มใหม่ แล้วบันทึกบริการ ข้อเสนอเพื่อพัฒนา สร้าง Job source ad_hoc ที่มอบหมายให้ช่างผู้บันทึกโดยอัตโนมัติ พร้อม ServiceEvent จริง เพื่อให้ Owner มองเห็นทุกงานโดยไม่ต้องสร้างแผนล่วงหน้า

กรณีลูกค้าขอให้ดูอีกเครื่องระหว่างงาน ช่างกด บันทึกงานเพิ่ม ใช้ Customer และ Location เดิม เลือกเครื่องเดิมหรือเพิ่มใหม่ ไม่ต้องโทรให้ร้านสร้างงานก่อน ข้อเสนอเพื่อพัฒนา เพิ่ม ServiceEvent ใน Job ที่ยังเปิดอยู่ ถ้า Job เสร็จแล้วให้สร้าง ad_hoc Job ใหม่เชื่อมบริบทเดิม

### 10.4 การปิดงาน

ตรวจเฉพาะข้อมูลที่จำเป็น เช่น ร้าน ลูกค้า สถานที่ ผู้บันทึก วันที่บริการ ประเภทบริการ และอุปกรณ์ที่ทำจริง โดยรายละเอียดขั้นต่ำที่ไม่ทราบสามารถใช้ข้อมูลระบุเครื่องเบื้องต้นได้ ไม่บังคับ OCR พิกัด serial ประวัติติดตั้ง และรอบดูแล ไม่บังคับรูปครบทุกประเภทในทุกธุรกิจ

ข้อเสนอเพื่อพัฒนา บันทึก draft ระหว่างขั้นตอนและแสดงสถานะการอัปโหลด หากรูปยังส่งไม่ครบต้องไม่แสดงว่าครบแล้ว การรองรับ offline และความหมายของ completed ระหว่างรอ sync ต้องตกลงตามหัวข้อ 16

## 11 ServiceEvent รูปภาพและประวัติ

### 11.1 แยกแผนงานจากสิ่งที่ทำจริง

ServiceEvent คือเหตุการณ์บริการที่เกิดขึ้นจริง ตัวอย่าง Job วางแผนซ่อมแอร์ แต่เหตุการณ์จริงบันทึกว่า พบ capacitor เสีย เปลี่ยน capacitor และทดสอบใช้งานปกติ งานหนึ่งมีหลายเหตุการณ์ได้ และเหตุการณ์หนึ่งใช้กับหลายเครื่องได้เมื่อข้อมูลบริการร่วมกัน

| ประเภท | ชื่อในหน้าจอ |
| --- | --- |
| installation | ติดตั้ง |
| maintenance | ล้างหรือบำรุงรักษา |
| repair | ซ่อม |
| inspection | ตรวจเช็ก |
| replacement | เปลี่ยน |
| other | อื่น ๆ |

ข้อเสนอแบบจำลอง ใช้ ServiceEvent เป็นหัวรายการร่วมและ ServiceEventEquipment เก็บผลรายเครื่อง เช่น สิ่งที่พบ สิ่งที่ทำ ผลการทดสอบ และรอบถัดไป หาก service type ต่างกันให้แยก ServiceEvent ภายใน Job เดียว เพื่อให้ history ของแต่ละเครื่องถูกต้อง

### 11.2 รูปและประวัติ

รูปมีประเภท equipment before after และ other เก็บเวลาและผู้ถ่ายหรือผู้อัปโหลด ผูก ServicePhoto กับเหตุการณ์และเครื่องที่เกี่ยวข้อง ไม่ใส่ GPS ในรูปเป็นข้อบังคับ และไม่ใช้พิกัดรูปแทน CustomerLocation

EquipmentPhoto ใช้ระบุป้ายและตัวเครื่องเพื่อ reuse ServicePhoto เป็นหลักฐานงานแต่ละครั้ง ภาพต้นฉบับต้องอ่านป้ายได้และมี thumbnail สำหรับรายการ แสดงจำนวนรูปที่ส่งสำเร็จและรูปที่กำลังรอ ไม่ให้ผู้ใช้สับสน

Timeline รายเครื่องแสดงวันที่ ประเภท ช่าง สรุปงาน รูป และรอบถัดไป เข้าจากลูกค้า สถานที่ อุปกรณ์ หรือผลค้นหาได้ เมื่อเปลี่ยนช่างยังเห็นข้อมูลที่จำเป็นต่อการให้บริการรอบต่อไป

ข้อเสนอเพื่อพัฒนา หลัง completed ให้แก้ผ่านสิทธิ์และมี audit trail ของค่าเดิมและใหม่ ไม่แก้ผลจริงย้อนหลังโดยไม่มีร่องรอย การเปลี่ยนชื่ออุปกรณ์ไม่ควรทำให้ความหมายประวัติเดิมหายไป

## 12 รอบบำรุงรักษาและวงจรบริการซ้ำ

### 12.1 MaintenanceSchedule

รอบดูแลผูกกับ Equipment ไม่ผูกลูกค้าอย่างเดียว เครื่องในสถานที่เดียวกันมีรอบต่างกันได้ ให้เลือก 3 เดือน 6 เดือน 12 เดือน กำหนดเอง หรือไม่ต้องเตือน โดยแสดงวันถัดไปให้ตรวจสอบก่อนบันทึก

ตัวอย่าง วันที่บริการ 2 ตุลาคม 2026 รอบ 6 เดือน → วันที่ดูแลถัดไป 2 เมษายน 2027 ไม่บังคับกำหนดรอบสำหรับงานที่ไม่ต้องดูแลซ้ำ

ข้อเสนอเพื่อพัฒนา คำนวณเดือนปฏิทินจากวันบริการจริง หากวันที่ไม่มีในเดือนเป้าหมายใช้วันสุดท้ายของเดือน เช่น 31 สิงหาคม + 6 เดือน → วันสุดท้ายกุมภาพันธ์ เก็บช่วงและหน่วยแยกจากวันครบกำหนด ใช้ timezone ร้านสำหรับรายการถึงรอบ

### 12.2 Owner maintenance screen

Owner เห็นเกินกำหนด ภายใน 7 วัน และภายใน 30 วัน พร้อมลูกค้า เบอร์ สถานที่ เครื่อง ภาพ วันที่บริการล่าสุด วันถึงรอบ ปุ่มโทรและนัดหมาย ต้องระบุใน UI ว่า 30 วันรวม 7 วันหรือไม่ เพื่อไม่ให้ตีความยอดซ้ำ

ข้อเสนอเพื่อพัฒนา ใช้รายการภายใน 7 และ 30 วันเป็นช่วงสะสมอย่างมีป้ายกำกับ ส่วนยอดรวมแยกรายการไม่ซ้ำ เกินกำหนดเมื่อวันครบกำหนดก่อนวันปัจจุบัน วันนี้ถึงรอบต้องมีรายการแสดงชัดเจน

### 12.3 นัดรอบใหม่และ reset รอบ

Owner ติดต่อลูกค้า เมื่อตกลงจึงกดนัดหมาย ระบบเติม Customer Location พิกัด Equipment และประเภทดูแลเดิม Owner เลือกวันเวลาและช่าง ไม่ต้องกรอกข้อมูลเครื่องใหม่ ไม่สร้างนัดอัตโนมัติจากวันถึงรอบโดยไม่มีการยืนยัน

ข้อเสนอเพื่อพัฒนา เชื่อมรอบที่นำไปนัดกับ Job เพื่อเตือนเมื่อมีนัดอยู่แล้ว การสร้างนัดยังไม่ถือว่าบริการสำเร็จและไม่ reset วันรอบ เมื่อบริการจริงเสร็จจึงคำนวณรอบถัดไปจาก service date ใหม่ ถ้ายกเลิกนัดให้รอบเดิมยังค้างและกลับมาติดต่อได้

การซ่อมหรือตรวจเช็กระหว่างรอบไม่ควรเลื่อนรอบล้างโดยอัตโนมัติ ให้ผู้ใช้เลือกหรือใช้นโยบาย service type ที่ตกลงไว้ ข้อเสนอ MVP ใช้หนึ่งรอบดูแล active ต่อเครื่อง ถ้าต้องการหลายแผนต่อเครื่องให้ขยายแบบจำลองภายหลัง

### 15.3 Constraints และแนวทาง schema

• ข้อมูลธุรกิจมี organization_id และ foreign key ที่กันการเชื่อมข้ามร้านได้

• member หนึ่งบัญชีต่อร้านไม่ซ้ำ ใช้ unique organization_id และ user_id

• junction ไม่ซ้ำตามคู่รหัสที่เกี่ยวข้อง แต่ Serial ไม่ต้อง unique ทั่วระบบ

• latitude longitude ว่างพร้อมกันหรือมีพร้อมกัน ค่าอยู่ในช่วงที่ถูกต้อง

• วันติดตั้ง brand model serial และพิกัด nullable ตาม Progressive Data

• index ตาม organization ร่วมกับ phone search schedule date status assignee และ serial

• timestamps created_at updated_at เก็บผู้สร้างและแก้สำหรับข้อมูลสำคัญ

• soft delete หรือ archive ต้องรักษา history และไม่คืน record ที่ซ่อนแล้วในผลค้นหาปกติ

ข้อเสนอด้านสถาปัตยกรรมจากแนวคิดเดิมคือ React Native และ Expo พร้อม TypeScript Backend Node.js PostgreSQL และ S3 compatible storage โดยยังไม่ถือเป็น stack ที่ล็อก ต้องแยก auth OCR notification และ integration ออกจาก core business rules

## 16 ความปลอดภัยและความน่าเชื่อถือ

### 16.1 Tenant isolation และ authorization

Backend resolve Organization จาก authenticated membership และตรวจ permission ทุกคำขอ ห้ามเชื่อ organization_id จากแอปเพียงอย่างเดียว ตรวจ object ที่อ้างด้วย ID ทั้ง Customer Location Equipment Job Media และ Schedule และตรวจที่ search export thumbnail OCR และ push ด้วย

ข้อเสนอเพื่อพัฒนา ใช้ database policy หรือ query scope ร่วมกับ composite foreign keys ตามสถาปัตยกรรม ทดสอบร้าน A ขอข้อมูลร้าน B ทั้งด้วย API และ URL รูปแล้วต้องถูกปฏิเสธ ไม่ให้ signed URL อายุยาวกลายเป็นช่องทางเผยแพร่ถาวร

### 16.2 Identity และ media

Join Link เป็นทางส่งคำขอ ไม่ใช่ bearer credential เพื่ออ่านร้าน ใช้ token ที่เดายาก reset ได้ rate limit การขอเข้าร่วมและ OTP session เก็บใน secure storage ไม่เก็บเป็น plain text ผู้ถูก suspend หรือ remove ต้องใช้ token เก่าเข้าถึงข้อมูลต่อไม่ได้

Media อยู่ใน private storage จำกัดประเภทและขนาดไฟล์ อนุญาตอ่านตามร้านและสิทธิ์ ใช้ URL ที่หมดอายุ ไม่ส่งข้อมูลส่วนบุคคลที่ไม่จำเป็นให้ OCR provider กำหนด retention deletion backup และ restore ก่อน production พร้อมทดสอบกู้คืน

### 16.3 Retry และความถูกต้อง

ข้อเสนอเพื่อพัฒนา ใช้ idempotency key กับการสร้าง Job ServiceEvent และ complete job การปิดงานต้องบันทึก history schedule และสถานะอย่างสอดคล้องกัน Notification ทำภายหลังและ retry ได้โดยไม่สร้างบริการซ้ำ

ต้องแจ้งความต่างระหว่าง บันทึกแล้ว รออัปโหลด และส่งไม่สำเร็จ ห้ามแสดงว่าบันทึกบน server สำเร็จเมื่อยังไม่สำเร็จ เก็บ draft ไม่ให้รูปและข้อมูลหายเมื่อ OCR ล้มเหลวหรือเครือข่ายชั่วคราวขัดข้อง

### 16.4 Offline resilience

แนวคิดเดิมเสนอ offline first สำหรับพื้นที่สัญญาณไม่ดี ข้อเสนอขั้นต่ำคือเก็บ draft และรูปในเครื่อง คิว retry และแจ้ง pending sync โดย OCR ไม่ขวาง workflow Full offline สำหรับ login ค้นฐานข้อมูลและ assignment ทั้งหมดต้องตัดสินใจเป็น scope แยก

หากรับ offline completion ให้ปิดเฉพาะในเครื่องพร้อมป้าย รอส่งข้อมูล Owner เห็น completed เมื่อ server รับสำเร็จแล้ว การ sync ต้องจัดการ conflict เช่น Owner ยกเลิกหรือเปลี่ยน assignment ระหว่าง offline และต้องไม่ส่งข้อมูลข้ามร้านหลังสลับร้าน

เป้าหมาย latency availability ปริมาณข้อมูลต่อร้าน อายุ session และแผน retention ต้องกำหนดจาก pilot ก่อน production ไม่ถือว่าตัวเลขที่ยังไม่มีการทดสอบเป็น SLA ที่รับประกัน

## 21 Subscription ของร้าน

### ราคา สิทธิ์ และรอบสมาชิก

Subscription ผูก organization_id ไม่ผูก Owner คนใดคนหนึ่ง การเปลี่ยนเจ้าของร้านไม่ทำให้สมาชิกหรือเอกสารการเงินหาย Owner active เป็นผู้ดูแพ็กเกจและชำระเงิน ช่างไม่ต้องสมัครแบบเสียเงินแยกและไม่เห็นบัตร ยอดเงิน หรือเอกสารผู้ซื้อ

กำหนด package code และเวอร์ชันแยกจาก price version แต่ละราคาเก็บ currency amount_minor และรอบ month หรือ year ราคาและสิทธิ์ที่เผยแพร่แล้วเป็น immutable รอบที่ชำระแล้วใช้ snapshot ของเวอร์ชันเดิม การเปลี่ยนราคาในอนาคตแจ้งและให้ Owner ยืนยันก่อนใช้กับรอบใหม่ตามนโยบาย

ราคา ชื่อแพ็กเกจ ระยะทดลองใช้ ระยะผ่อนผัน และขีดจำกัดยังไม่ตกลง ตัวเลข 14 วัน 7 วัน และราคาบนภาพต้นแบบเป็นตัวอย่างเท่านั้น ค่า production ต้องตั้งและเผยแพร่ด้วยผู้ดูแลที่มีสิทธิ์ ก่อนเปิดให้ร้านสมัครจริง

ข้อเสนอ MVP วัด active technician seats พื้นที่ภาพ และ OCR ต่อรอบสมาชิก จำนวน Owner ไม่ใช้ seat; pending rejected suspended removed ไม่ใช้ seat การอนุมัติหรือเปิดช่างกลับ active ตรวจ quota แบบ atomic ป้องกันสองคำขอทำให้เกินจำนวน คำขอที่รออยู่ไม่ถูกลบเมื่อเต็ม

ข้อมูลลูกค้า เครื่อง และประวัติงานไม่ถูกตัดทิ้งเมื่อ downgrade หากสมาชิก active มากกว่าขีดจำกัดใหม่ ให้ Owner เลือกช่างที่จะคง active ก่อน downgrade มีผล หากยังไม่เลือกให้พักคำขอเปลี่ยนแพ็กเกจ ไม่ตัดช่างตามลำดับอัตโนมัติ พื้นที่เกินหยุด upload ใหม่ แต่ยังอ่านไฟล์เดิมและบันทึกบริการโดยไม่บังคับรูปได้ OCR เต็มใช้กรอกเองได้

### การเริ่มใช้และต่ออายุ

สมัครร้าน → ยืนยันตัวตน → เริ่ม trial ถ้าแพ็กเกจอนุญาต หรือเลือกชำระ → เลือก plan และรอบ → ตรวจราคาและข้อมูลผู้ซื้อ → สร้าง invoice และ payment attempt → รับเงินยืนยัน → เปิดช่วงสมาชิกและสิทธิ์ → ส่งแจ้ง Owner ทุกขั้น retry ได้โดยไม่สร้าง invoice หรือ subscription ซ้ำ

Billing period ใช้ช่วงเวลาเริ่มรวมและสิ้นสุดไม่รวม [start_at,end_at) โดย server เป็นผู้คำนวณ สำหรับการต่อก่อนหมดอายุ ให้ต่อจากปลายรอบเดิม ไม่หักวันเดิม หากมี future period ของ invoice เดิมแล้วคืนช่วงเดิมเมื่อ retry หลัง expired ข้อเสนอเริ่มรอบใหม่จากเวลารับเงินยืนยัน คงข้อมูลประวัติเดิมทุกชุด

Upgrade หรือ downgrade ใน MVP มีผลต้นรอบถัดไป แสดงราคากับวันมีผลก่อนยืนยัน ไม่คำนวณส่วนต่างกลางรอบแบบซ่อน หากต้องเพิ่มสิทธิ์ทันทีใช้คำขอ entitlement grant แยก มีวันหมดอายุและ audit แล้วพัฒนา proration เป็น flow เฉพาะภายหลัง สิทธิ์ฟรีชั่วคราวไม่ถูกนับเป็นเงินรับหรือ invoice paid

หยุดต่ออายุเป็น cancel_at_period_end ยังคงใช้ถึง end_at ที่ชำระแล้ว การยกเลิกคำขอนี้ทำได้ก่อนจบรอบ การหยุดต่ออายุไม่ได้แปลว่าคืนเงิน การคืนเงินมีคำขอ ผลรับเงินจริง และผลต่อสิทธิ์เป็นคนละการตัดสินใจ

### การรับเงินและความน่าเชื่อถือ

รองรับสองช่องทางในแบบออกแบบ: manual transfer พร้อมหลักฐานและตรวจรายการรับจริง หรือ hosted checkout ของผู้ให้บริการที่เลือก Hosted checkout ไม่ทำให้ระบบเราเก็บเลขบัตรหรือ CVV รูปสลิปและการกลับจากหน้าจ่ายเงินเป็นเพียงหลักฐานหรือสถานะรอ ไม่ใช้เปิดสิทธิ์โดยอัตโนมัติ

Manual transfer: Owner ส่งหลักฐานส่วนตัว → Billing Operator ตรวจยอด สกุลเงิน และ reference กับรายการรับจริง → ยืนยันหรือขอข้อมูลใหม่ → commit payment invoice period และ entitlement พร้อม audit การ reject ไม่ลบหลักฐานเดิมและไม่ทำให้รอบเดิมหยุด

Online payment: ตรวจ signature ของ webhook ตาม provider และเก็บเหตุการณ์ที่รับแล้วแบบ durable ก่อนตอบ acknowledgement → worker ตรวจ latest provider state และจัดการเหตุการณ์ซ้ำหรือมาผิดลำดับ → commit ผล → reconciliation ตรวจเงินกับสิทธิ์ซ้ำตามรอบ ห้ามลดสิทธิ์เพราะ payment_failed เก่าที่มาหลัง payment_succeeded

Refund: ผู้ขอระบุยอด เหตุผล invoice และผลต่อสิทธิ์ → ผู้อนุมัติอีกคนตรวจวงเงินและยอดคงเหลือ → adapter ทำรายการ → บันทึก success เมื่อยืนยันการคืนจริงเท่านั้น Partial refund เก็บแยก ไม่เปลี่ยนยอดรับเดิมย้อนหลัง หากล้มเหลวแสดง retry แบบ idempotent ไม่สร้างรายการคืนซ้ำ

## 22 สถานะสิทธิ์และข้อจำกัด

subscription.status เป็น trialing pending_payment active past_due expired ended ส่วน invoice payment และ organization มีสถานะของตนเอง Active membership ไม่ได้หมายถึงแพ็กเกจ active ทั้งสองต้องผ่านร่วมกัน คำสั่งแต่ละประเภทใช้ effective entitlement ที่คำนวณจาก period และ grant ที่ยัง valid

pending_payment ใช้เมื่อยังไม่มี trial หรือ paid period ที่ valid Owner เข้าหน้าชำระและช่วยเหลือได้ แต่ไม่มีสิทธิ์สร้างงาน ส่วน invoice ต่ออายุที่ยังรอตรวจไม่เปลี่ยน subscription active ของรอบเดิม การหยุดต่ออายุโดยตั้งใจเข้าสู่ ended เมื่อจบรอบ ไม่ใช้ grace ของการชำระล้มเหลวอัตโนมัติ

| สถานะ | Owner | Technician | รอบดูแลและข้อมูล |
| --- | --- | --- | --- |
| trialing active | ใช้สิทธิ์ตามแพ็กเกจ | งานที่มอบหมายและหน้างาน | บันทึกและวนรอบบริการได้ |
| past_due ภายใน grace | ใช้งานตามสิทธิ์เดิม เห็นเตือนชำระ | ทำงานต่อได้ ไม่เห็นข้อมูลเงิน | แจ้งเตือนรอบดูแลตามปกติ |
| expired หรือ ended | อ่านประวัติ ต่ออายุ ขอ export | อ่านงานตนเองที่เคยมีสิทธิ์; ไม่สร้างบริการใหม่ | คง due และ history ไม่ลบ |
| งานที่เริ่มก่อนหมดอายุ | ดูผลส่งที่เข้าเงื่อนไขได้ | ส่ง draft เดิมภายในช่วงที่ตั้งไว้ | ห้ามเปิดงานใหม่ใช้ช่องทางนี้ |
| organization suspended | ไม่มีสิทธิ์ข้อมูลธุรกิจ ติดต่อทีมได้ | ไม่มีสิทธิ์ข้อมูลธุรกิจ | ข้อมูลคงอยู่ worker ธุรกิจพัก |
| membership suspended removed | ตามสิทธิ์สมาชิกที่ยัง active | บัญชีนั้นเข้าไม่ได้ | ประวัติผู้ทำเดิมยังอยู่ |

ข้อเสนอ billing grace ใช้สิทธิ์เดิมต่อได้ถึง grace_until และแจ้ง Owner เท่านั้น ไม่บังปุ่มบันทึกงานของช่าง เมื่อ expired ห้ามสร้าง Job ใหม่ เริ่มบริการใหม่ อนุมัติช่าง หรือเพิ่มอุปกรณ์ใหม่ Owner ยังอ่านข้อมูลและขอ export ช่างดูประวัติและงานในขอบเขตเดิมแบบ read only

ข้อเสนอส่งงานค้างหลังหมดอายุให้ไม่เกิน 24 ชั่วโมงเฉพาะ Job ที่เริ่มก่อน end_at ด้วยสมาชิกและ assignment เดิม ต้องไม่มี security suspension และรับเฉพาะผลบริการจากงานนั้น ไม่เพิ่มงานใหม่ นโยบายนี้ตั้งค่าได้และต้องตรวจบน server Offline draft ที่อ้างเวลา client อย่างเดียวไม่ได้รับข้อยกเว้น

เมื่อ expired เก็บ maintenance cycle และ due เดิม worker แจ้งสถานะสมาชิกแก่ Owner ได้ แต่พักแจ้งเตือนธุรกิจรายวันและการสร้างนัด เมื่อกลับ active คำนวณ due ปัจจุบันและสรุปงานค้าง ไม่ reset รอบและไม่ส่งทุก reminder ที่พลาดย้อนหลัง

Organization suspension ด้านความปลอดภัยมีผลเหนือ paid period และ grant ทุกชนิด Support contact และ billing status ที่ไม่ใช่ข้อมูลลูกค้าสามารถเข้าผ่านช่องทางช่วยเหลือที่กำหนด การคืนสิทธิ์ร้านคืนตาม subscription เดิม ไม่สร้าง paid period ใหม่

### 23.1 Support access

Support เห็น metadata ร้านและสถานะเทคนิคที่ปิดบังข้อมูลก่อน หากต้องดูเนื้อหาบริการ ให้ขอ grant ระบุ ticket organization target scope read only ระยะเวลา และเหตุผล ต้องได้รับอนุมัติจาก Owner และผู้อนุมัติแพลตฟอร์มตามสิทธิ์ ไม่ใช้ปุ่ม impersonate Owner ที่มีอำนาจทุกอย่าง

เจ้าของร้านเห็นและเพิกถอน support grant ได้ ทุก read ที่เปิดเนื้อหามี audit เมื่อหมดอายุ API และ media ปฏิเสธทันที URL ที่ออกแล้วมีอายุสั้น กรณีฉุกเฉิน break glass ต้องระบุ incident มีผู้อนุมัติอีกคน scope จำกัด และแจ้งร้านย้อนหลังตามนโยบาย ห้ามถือว่าบทบาท Super Admin คือ consent ของร้าน

## 24 การดูแลข้อมูล ระบบ และการเงิน

เนื้อหางานลูกค้าของร้านแยกจากข้อมูลลูกค้าผู้ซื้อสมาชิกของแพลตฟอร์ม Admin search เริ่มจากข้อมูลร้านและ masked owner data ไม่ค้นเบอร์ลูกค้าปลายทางหรือภาพทุก tenant เพื่อความสะดวก ระบบ export เก็บ request scope ผู้ขอ ผู้อนุมัติ เวลา และ audit

การขอลบข้อมูลไม่ใช่การลบ cascade ทันที ตรวจผู้ขอ security hold financial records และ retention ก่อนแสดงข้อมูลที่จะลบหรือ anonymize คำขอมี cooling period ที่ตั้งได้ ข้อมูลใน backup หมดอายุตามวงจร backup หาก restore ต้อง replay deletion log ก่อนกลับบริการ ห้ามรับประกันลบสำเนาทุกแห่งทันที

Invoice และ receipt สมาชิกเป็นเอกสารของแพลตฟอร์ม ไม่ใช่ใบงานหรือใบกำกับที่ร้านออกให้ลูกค้าของร้าน ชื่อผู้ซื้อ ที่อยู่ เลขภาษี branch และชนิดเอกสารเป็น field ที่ตั้งค่าได้ ข้อกำหนดภาษี การใช้ e tax และเอกสารคืนเงินต้องตรวจตามกระบวนการบริษัทก่อนผลิตเอกสารจริง ไม่กำหนดอัตราภาษีในแบบนี้

รายงานการเงินแยกยอดเรียกเก็บ ยอดรับจริง คืนเงิน และเงินรอตรวจ ไม่ใช้ invoice open เป็นรายได้ที่รับแล้ว MRR เป็นมูลค่าสมาชิก recurring ที่ normalize ตามเดือน ไม่เท่ากับ cash received รายปี และต้องระบุการรวม discount grace trial refund กับสกุลเงิน ห้ามรวมต่างสกุลเงินโดยไม่มีกติกาแปลง

ทีม Operations ตรวจ queue lag failed uploads OCR failures webhook retry storage backup age และ restore drills Alerts ไม่บรรจุข้อมูลลูกค้าหรือ secret การ replay outbox และ webhook ผ่านคำสั่ง idempotent พร้อมเหตุผล ไม่แก้แถว production แบบไม่มีประวัติ
