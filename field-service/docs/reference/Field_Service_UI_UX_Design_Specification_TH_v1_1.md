ชื่อเอกสารและชื่อระบบเป็นชื่อกลาง ยังไม่ผูกกับชื่อผลิตภัณฑ์สุดท้าย ABC AIR และข้อมูลลูกค้าในภาพเป็นตัวอย่าง

### แนวทางที่ใช้เป็นฐาน

ใช้หน้าตาเรียบง่ายที่มีบุคลิกจากสีเขียวอมฟ้า เขียวมะนาว และอำพันตามต้นแบบที่ยอมรับแล้ว รักษาขั้นตอนสั้นและข้อมูลเดิมที่นำกลับมาใช้ได้ เอกสารนี้ระบุหน้าจอ เส้นทางการใช้งาน กติกาสถานะ องค์ประกอบ และเกณฑ์ตรวจรับ เพื่อส่งต่อทีมออกแบบ พัฒนา และทดสอบ

เอกสารนี้ใช้งานร่วมกับ Product and Functional Specification ฉบับ 1.1 โดยข้อกำหนด GPS แยก Job และ ServiceEvent ข้อมูลหลายอุปกรณ์ และการไม่ให้ AI ขวางงานยังคงเป็นเงื่อนไขหลัก

### สถานะของแบบ

Visual direction ใช้เป็น baseline สำหรับรอบนี้ ส่วนชื่อผลิตภัณฑ์และสีขั้นสุดท้ายปรับได้ภายหลัง ต้นแบบภาคสนามแสดง 50 states และส่วน Subscription กับ Platform Console เพิ่ม 37 states รวม 87 หน้าจอและสถานะ เส้นทางหลักกดลองได้ แต่การส่ง SMS โทร กล้อง GPS push อัปโหลด และธุรกรรมบน server เป็นการจำลอง การผ่านต้นแบบไม่ใช่การรับรองระบบ production

## 1 เป้าหมายประสบการณ์และหลักออกแบบ

ช่างเปิดแอปแล้วต้องรู้ทันทีว่างานใดควรทำต่อ อยู่ที่ไหน และต้องทำอะไร เจ้าของร้านต้องเห็นสิ่งที่ต้องลงมือ เช่น งานรอมอบหมาย คำขอเข้าร่วมทีม และอุปกรณ์ถึงรอบ เพื่อเปลี่ยนข้อมูลบริการให้เกิดนัดใหม่

| หลัก | การตัดสินใจใน UI |
| --- | --- |
| Technician First | หน้าวันนี้และรายละเอียดงานนำด้วยเวลา ลูกค้า สถานที่ และปุ่มหลัก |
| หนึ่งหน้าหนึ่งการตัดสินใจหลัก | รับงานแบ่งลูกค้า สถานที่ และนัด โดยมี review ก่อนส่ง |
| Camera First | มีทางเข้ากล้องป้ายและรูปงาน แต่มีทางกรอกหรือข้ามทุกครั้ง |
| Progressive Data | ยังไม่รู้พิกัดหรือ Serial ไม่ขวางการรับงาน |
| Capture Once Reuse Forever | ค้นลูกค้าเดิม เลือกสถานที่และเครื่องเดิม ไม่สร้างซ้ำโดยอัตโนมัติ |
| AI Assists Never Blocks | ผล OCR เป็นข้อเสนอ รูปถูกเก็บและไปต่อได้ |
| Installation Is Optional | ไม่มีวันที่ติดตั้งก็เพิ่มเครื่องและดู timeline ได้ |
| QR equipment optional | QR ของร้านใช้ Join ส่วนอุปกรณ์ไม่ต้องติด sticker |
| Don’t Become ERP | ไม่มีเมนู stock invoice payroll หรือบัญชีในเมนูหลัก |

เป้าหมาย Under One Minute ใช้กับการบันทึกบริการทั่วไปที่มีข้อมูลเดิม ไม่นับเวลาบริการจริง การเดินทาง หรือการสร้างลูกค้าและอุปกรณ์หลายเครื่องครั้งแรก ต้องวัดเวลาจากผู้ใช้จริงก่อนยืนยันเป้าหมาย

### 1.1 ลำดับข้อมูล

งานวันนี้แสดง เวลา → ลูกค้า → ประเภทและจำนวนเครื่อง → สถานที่ → สถานะ รายละเอียดงานแสดง นัด → ช่องทางติดต่อและสถานที่ → อาการ → เครื่อง → ประวัติ → ปุ่มเริ่มหรือบันทึกต่อ ข้อมูล model และ serial อยู่ในรายละเอียดเครื่อง ไม่แย่งพื้นที่หัวงาน

### 1.2 สิ่งที่ไม่เพิ่มภาระช่าง

ไม่บังคับบันทึก installation ก่อน service ไม่บังคับ Serial ทุกเครื่อง ไม่บังคับ QR sticker และไม่บังคับบันทึกพิกัดก่อนเสร็จงาน รูปก่อนและหลังเป็นขั้นตอนที่ส่งเสริมให้ทำ แต่กฎการบังคับภาพต้องเลือกตามประเภทธุรกิจ ไม่บังคับเหมือนกันทุกงาน

## 2 โครงสร้างเมนูและเส้นทางหลัก

| บทบาท | เมนู | หน้าที่ |
| --- | --- | --- |
| Owner | หน้าแรก | ภาพรวมงานวันนี้ รายการติดตาม ปุ่มสร้างงาน |
| Owner | งาน | งานทั้งหมดในร้าน คัดตามวัน สถานะ และช่าง |
| Owner | ลูกค้า | ค้นลูกค้า เบอร์ สถานที่ อุปกรณ์ และประวัติ |
| Owner | เพิ่มเติม | ทีมช่าง ลิงก์เข้าร้าน ข้อมูลร้านและบัญชี |
| Technician | วันนี้ | งานของตนตามเวลานัด |
| Technician | งาน | งานที่มีสิทธิ์เข้าถึงและงานหน้างานของตน |
| Technician | ค้นหา | ลูกค้าและอุปกรณ์ภายใต้สิทธิ์ที่ backend กำหนด |
| Technician | เพิ่มเติม | ข้อมูลผู้ใช้ ร้าน และงานที่บันทึกหน้างาน |

ก่อนสร้างร้าน หรือขณะรออนุมัติ ถูกระงับ และลิงก์ใช้ไม่ได้ ต้องซ่อนเมนูข้อมูลธุรกิจ ไม่ใช้เพียงการปิดปุ่มเพื่อแทนการตรวจสิทธิ์ เมื่อเข้าใช้งานแล้วรักษา session อย่างปลอดภัย ไม่ต้อง login ใหม่ทุกวัน

### 2.1 เส้นทางเริ่มต้น

Owner  เริ่มใช้งาน → สร้างร้าน → ยืนยันเบอร์ → ร้านพร้อมใช้ → แชร์ Join Link → รับงานแรก

Technician  เปิด Join Link → เห็นชื่อร้าน → ใส่ชื่อ → ขอเข้าร่วม → รออนุมัติ → เข้า วันนี้

### 2.2 เส้นทางรับงานและบริการ

Owner  สร้างงาน → ค้นลูกค้า → ใช้เดิมหรือเพิ่มใหม่ → เลือกหรือเพิ่มสถานที่ → นัดและมอบหมาย → ตรวจ → ยืนยัน

Technician  วันนี้ → รายละเอียด → เริ่มงาน → เลือกหรือเพิ่มเครื่อง → บันทึกบริการจริงและรูป → รอบดูแล → ตรวจเครื่องที่ทำจริง → เสร็จงาน

### 2.3 เส้นทางงานครั้งถัดไป

Owner  ถึงรอบดูแล → โทรคุย → นัดจากข้อมูลเดิม → เลือกวันและช่าง → ยืนยัน → ช่างใหม่เห็นเครื่อง ภาพ ประวัติ และพิกัดสถานที่เดิม

แบบภาพรวมงานและแบบงานถัดไปเป็นทางเลือกของหน้า วันนี้ ใช้ข้อมูลและเส้นทางเดียวกัน ข้อเสนอรอบพัฒนาคือให้ งานถัดไป เป็น entry ที่เด่นและมีรายการงานที่เหลือ ผู้ใช้เปิดงานทั้งหมดได้จากเมนู งาน การเลือก layout สุดท้ายต้องทดสอบกับช่าง

### 3.2 Typography และระยะ

| รายการ | ข้อเสนอสำหรับ implementation |
| --- | --- |
| Font ภาษาไทย | Noto Sans Thai หรือ font ไทยที่ platform รองรับอย่างเหมาะสม |
| Heading หลัก | 24–28 sp น้ำหนัก 500 |
| Heading ย่อย | 16–18 sp น้ำหนัก 500 |
| Body และปุ่ม | 14–16 sp ไม่ใช้ thin font |
| Editable input | 16 sp ขึ้นไป |
| Metadata | 12 sp; ข้อมูลที่ต้องตัดสินใจไม่เล็กกว่า body |
| Spacing scale | 4 8 12 16 20 24 32 หน่วยตาม platform |
| ขอบหน้าจอ | 16–20 dp รวม safe area |
| Touch target | อย่างน้อย 44 × 44 dp; action สำคัญสูงประมาณ 50 dp |
| Corner | input และปุ่ม 12–15 dp; card 18 dp; hero 24 dp |
| Shadow | เบามาก ใช้แยก layer ไม่ทำทุกองค์ประกอบลอยเด่น |
| Breakpoints | 320–430 dp สำหรับมือถือ ใช้ max content width บนหน้าจอใหญ่ |

sp และ dp เป็นแนวทางสำหรับการพัฒนาบนมือถือ ต้นแบบ HTML ใช้ px ในการจำลอง ต้องแปลงให้ตรงระบบ sizing และ text scaling ของ platform ไม่ล็อก screenshot pixel เป็นขนาดจริง

## 5 เริ่มใช้งานและจัดการทีม

### 5.1 Owner onboarding

A01 แสดงสองทางที่สื่อบทบาทชัด A02 ขอชื่อร้านและเบอร์เท่านั้น ไม่ใช้ฟอร์มบริษัทเต็ม เมื่อ valid ไป A03 ยืนยันเบอร์ ก่อนสร้าง User Organization และ owner membership เป็นธุรกรรมเดียวกัน A04 แสดงร้านพร้อมใช้ พร้อมลิงก์เดียวให้แชร์กับช่างทุกคน

Validation แสดง error ใต้ช่องที่ผิด ชื่อร้านตัดช่องว่างต้นท้ายได้ เบอร์ normalize ก่อนตรวจ แต่รักษารูปแบบที่ผู้ใช้เข้าใจ เมื่อ OTP ผิดให้แก้ในหน้าเดิมพร้อมค่าชื่อร้านไม่หาย แสดงเวลาส่งใหม่และ rate limit ตาม auth policy โดยไม่ใส่ข้อความเทคนิค

ต้นแบบใช้รหัส 123456 และไม่ส่ง SMS ของจริง รายละเอียด auth method และ recovery ต้องยืนยันกับทีมก่อน implement OTP rate limit และการกู้บัญชีไม่ถือว่าถูกออกแบบด้าน security เสร็จจากหน้าตาเพียงอย่างเดียว

### 5.2 Technician onboarding

A05 เปิดจาก Join Link ที่มีบริบทร้าน ต้องแสดงชื่อร้านก่อนส่งคำขอ ขอเพียงชื่อที่ใช้ในร้าน ไม่บังคับอีเมลหรือรหัสผ่าน การขอข้อมูล identity เพิ่มเพื่อกู้บัญชีต้องออกแบบโดยไม่เพิ่มขั้นตอนยาว

A06 รอ Owner อนุมัติ ปุ่ม ตรวจสอบสถานะ ไม่ให้สิทธิ์เอง ยังไม่มี bottom nav ของงาน การอนุมัติจริงเกิดจาก T01 เมื่อ backend ยืนยันจึง A07 เปิดงานวันนี้ ขณะรอห้าม cache หรือแสดงรายชื่อลูกค้า

A08 ลิงก์ถูก reset ปิด หรือใช้ไม่ได้ ให้ขอลิงก์ใหม่ ไม่เผยข้อมูลร้านโดยไม่จำเป็น คำขอซ้ำไม่สร้างสมาชิกซ้ำ ผู้ใช้ active เปิดลิงก์เดิมแล้วกลับเข้าร้านได้ ถ้าปฏิเสธคำขอให้ข้อความสุภาพและแนะนำติดต่อ Owner ห้ามแสดงเหมือนระบบเสีย

### 5.3 Owner team management

T01 แสดง reusable Join Link QR ที่ชี้ลิงก์เดียวกัน คำขอ pending และสมาชิก active กดอนุมัติหรือปฏิเสธตามรายการ ชื่อสมาชิกคงอยู่ใน Service History แม้นำออกภายหลัง

Dialog QR ใน production ต้องสร้าง QR ที่สแกนกลับเข้า Join flow ได้จริง ต้นแบบแสดง QR ที่เข้ารหัสลิงก์ตัวอย่าง พร้อม dialog เปิดปิดรับและยืนยัน reset แต่ URL ตัวอย่างยังไม่มี backend รับสมัครจริง

Owner ปิดรับเข้าได้โดยไม่ลบสมาชิกเดิม Reset Link ต้องยืนยันพร้อมข้อความ ลิงก์เดิมจะส่งคำขอใหม่ไม่ได้ แล้วแสดงลิงก์ใหม่ ปุ่มแชร์ใช้ share sheet ของมือถือ ค่า token จริงไม่แสดงใน logs

T02 ระงับและเปิดใช้สมาชิก T03 นำออกแบบ destructive confirmation ต้องตรวจงานที่ยังเปิดและให้ Owner จัด assignment ก่อน สมาชิก suspended หรือ removed ถูกปฏิเสธทุก API และ media ข้อมูล cached ต้อง lock และจัดการตาม security policy

## 6 รับงาน นัดหมาย และมอบหมาย

### 6.1 ค้นก่อนสร้าง

J01 เริ่มจากเบอร์โทร พบแสดงชื่อและจำนวนสถานที่ ไม่พบให้เพิ่มลูกค้าใหม่โดยใช้เบอร์ที่กรอกไว้ J02 รับข้อมูลขั้นต่ำ ป้องกันการสร้าง Customer ซ้ำจาก retry หรือกดปุ่มซ้ำ แต่เบอร์เดียวกันไม่จำเป็นต้องหมายถึงบุคคลเดียวเสมอ ให้เลือกและยืนยัน merge ต่างหากถ้ามีในอนาคต

J03 ลูกค้าเดิมมีหลายสถานที่ เลือกตามชื่อและที่อยู่ พร้อม label มีพิกัดหรือยังไม่มี ไม่ใช้ pin icon เพียงอย่างเดียว J04 เพิ่มสถานที่ ชื่อสถานที่จำเป็น ที่อยู่และจุดสังเกตช่วยให้เดินทางได้ พิกัดยังไม่บังคับ ไม่เปิด GPS อัตโนมัติขณะสร้างสถานที่

### 6.2 นัดและมอบหมาย

J05 ระบุประเภทบริการ วันเวลา และ Technician หรือยังไม่มอบหมาย แสดงอุปกรณ์ยังไม่ทราบและจำนวนประมาณได้ ไม่สร้าง Equipment สมมติจากจำนวนประมาณ ถ้ามีเครื่องเดิมให้เลือกด้วยภาพใน bottom sheet หรือหน้าเลือก โดยไม่เพิ่มฟอร์ม Serial ตอนรับสาย

J06 ทบทวนลูกค้า สถานที่ วันที่ เวลา ประเภท จำนวนประมาณ และช่างก่อนส่ง ปุ่มหลักใช้ชื่อที่ตรงผล เช่น ยืนยันและมอบหมายงาน หรือ สร้างงานรอมอบหมาย J07 success ต้องแสดงผลที่ server รับแล้ว ไม่อาศัย push สำเร็จเป็นเงื่อนไขสร้างงาน

เมื่อส่ง pending แสดงสถานะในปุ่มและป้องกันกดซ้ำ หากล้มเหลวรักษา input ทุกช่องและให้ลองใหม่ ช่างที่ถูก suspend หรือลบระหว่างสร้างงานต้องแจ้งและเลือกใหม่ งานไม่ถูกสร้างด้วย assignment ที่ใช้ไม่ได้

## 7 การทำงานของช่างและอุปกรณ์

### 7.1 เริ่มงานและสถานที่

J09 แสดงเวลา ลูกค้า เบอร์ สถานที่ หมายเหตุ อาการ เครื่อง และประวัติ ปุ่มโทรและนำทางอยู่ใกล้ข้อมูลสถานที่ กดเริ่มงานเปลี่ยน scheduled เป็น in_progress เท่านั้น ไม่มีการขอ GPS

ปุ่ม บันทึกตำแหน่งสถานที่ เป็นการกระทำแยก ขอ While Using the App อ่านเพียงครั้งเดียวแสดง accuracy ให้ตรวจและบันทึกลง CustomerLocation หยุดอ่านทันที หากมีพิกัดเดิมให้ confirm ก่อนเขียนทับ ช่างใหม่ใช้พิกัดเดิมนำทางได้

S13 ปฏิเสธสิทธิ์ GPS หรืออ่านไม่ได้ ทำบริการต่อได้ แสดงที่อยู่และลองใหม่ได้ ไม่ขอ Always และไม่บันทึกพิกัดจากรูป Start End Job หรือการเปิดหน้าจอ

### 7.2 เลือกและเพิ่มเครื่อง

S03 เลือกจากภาพและชื่อเรียก พร้อม Location และ brand/model เมื่อมี S02 เพิ่มจากป้ายและรูปตัวเครื่อง รองรับไม่มีป้าย ไม่มี serial และกรอกเอง ภาพเครื่องอาจเป็น placeholder จนเพิ่มภาพจริง

S08 OCR อ่านสำเร็จแสดงข้อเสนอแก้ได้ก่อนยอมรับ ค่าไม่แน่ใจ เช่น O/0 ต้องให้ผู้ใช้ตรวจ S09 อ่านไม่ได้ยังเพิ่มเครื่องหรือบันทึกบริการต่อได้ เมื่อผลมาช้าห้ามเขียนทับค่าที่ผู้ใช้แก้เงียบ ๆ S10 อาจซ้ำให้เลือกเดิมหรือยืนยันเป็นคนละเครื่อง ไม่ merge อัตโนมัติ

Installation ไม่เป็นขั้นตอนก่อนเพิ่มเครื่อง QR tag เครื่องไม่อยู่ใน core flow หน้าข้อมูลเครื่องแสดง installation ไม่ทราบได้ ไม่ใช้ข้อความที่บังคับย้อนกรอกประวัติ

### 7.3 บันทึกบริการจริง

S01 เริ่มด้วยเครื่องที่เลือก แสดงเครื่อง 1 จาก 3 เพื่อให้รู้บริบท เลือกประเภทที่ทำจริง ถ่ายรูปก่อนหลัง และบันทึกสิ่งที่พบ สิ่งที่ทำ ผลทดสอบ เมื่อต้องแก้ผลเฉพาะเครื่องให้แยกใน ServiceEventEquipment

จำนวนเครื่องใน Job เป็นแผน จำนวนที่เลือกก่อน complete เป็นสิ่งที่ทำจริง ถ้าทำ 2 จาก 3 ต้องสร้าง history เฉพาะ 2 และระบุรายการที่ไม่ได้ทำ หาก service type ต่างกันแบ่ง ServiceEvent ตามความหมาย แม้ใช้ปุ่มปิด Job เดียวกัน

รูป before after และ other ผูกกับ event และเครื่อง เก็บ timestamp และผู้บันทึก ไม่มีการเพิ่ม GPS metadata เป็นเงื่อนไข ภาพ pending upload มี indicator ลองส่งใหม่หรือลบได้ การปิดงานและ upload ต้องไม่ซ่อนสถานะค้าง

### 7.4 งานเพิ่มหน้างาน

S07 เปิดจาก บันทึกงานหน้างาน ใช้ลูกค้าและสถานที่เดิมหรือเพิ่ม minimal ได้ ไม่ต้อง Owner สร้าง Job ก่อน เมื่ออีกเครื่องเพิ่มระหว่าง Job เปิด ใช้บริบทเดิมและเพิ่ม actual service ถ้า Job เดิมจบแล้วสร้าง ad hoc Job ใหม่ตาม business rule

### 7.5 ตั้งรอบและเสร็จงาน

S04 เลือกเฉพาะเครื่องที่ทำจริง ตั้ง 3 6 12 เดือน กำหนดเอง หรือไม่เตือน S05 ตั้งต่างกันรายเครื่อง เช่น 6 3 และ 12 เดือน แสดงวันถัดไปก่อนยืนยัน การเปลี่ยนเป็นไม่เตือนต้องแสดงผลชัด

S06 สำเร็จเมื่อ server ยืนยัน event และสถานะ Job พร้อม schedule อย่างสอดคล้องกัน ถ้ายังอยู่ local ให้ S11 รอส่ง ไม่ใช้คำ เสร็จแล้ว ในความหมาย server เพื่อไม่ทำให้ Owner เข้าใจผิด การกดซ้ำต้อง idempotent

## 8 ประวัติและวงจรบริการซ้ำ

E01 และ E02 ใช้ layout เครื่องร่วมกัน แสดงชื่อ ภาพ Category Brand Model Serial Location Customer Timeline Service Type ผู้ทำ รูปและรอบถัดไป เปิด E03 ดูรูป before after และเวลาได้ ภาพที่ส่งไม่ครบไม่แสดงว่าเป็นชุดครบ

E04 ค้นชื่อลูกค้า เบอร์ brand model serial และ nickname ผลมีรูปและบริบทเพื่อแยกเครื่องที่คล้ายกัน Camera Search ใช้ OCR serial เป็นทางช่วย มีทางกลับค้นด้วยมือ ไม่พบให้สร้างใหม่โดยตรวจความซ้ำก่อน

M01 แสดงถึงรอบวันนี้ เกินกำหนด และภายในช่วง 7 หรือ 30 วัน ตัวเลขต้องระบุว่า cumulative หรือช่วงไม่ซ้ำ ใช้วันที่ใน timezone ร้าน ไม่ใช้จำนวน Job แทนจำนวนเครื่องที่ถึงรอบ

Owner โทรคุยแล้วกด M02 เติม Customer Location GPS และ Equipment เดิม เลือกวันและช่าง M03 review แล้วส่ง M04 ถ้ามีนัดแล้วแสดงวัน ช่าง และปุ่มดูนัด ป้องกันสร้างซ้ำจาก due record เดียว

การนัดหมายยังไม่ reset รอบ เมื่อบริการจริงเสร็จจึงคำนวณจาก service date ใหม่ งาน repair ระหว่างรอบไม่ควรเลื่อนรอบ maintenance โดยอัตโนมัติ ถ้ายกเลิกนัดรอบเดิมยังค้างให้ติดตามได้

### 9.1 Offline และการสลับร้าน

ขั้นต่ำเก็บ draft และรูป พร้อมสถานะ รอส่งข้อมูล retry ใช้ idempotency identifier เดิม ถ้า service server รับแล้วแต่รูปบางรูปค้าง ให้แสดง completed กับรูปค้างแยกกัน ถ้า event ทั้งชุดยัง local ห้ามแสดง server completed

S12 งานถูก cancel หรือ reassigned ระหว่าง offline ไม่ให้ write ทับ latest อัตโนมัติ เก็บ actual service ที่บันทึกไว้และให้คนที่มีสิทธิ์ตัดสินใจ ถ้าถูกระงับหรือ logout ไม่เปิด cached customer ให้ผู้ใช้อื่น และไม่ส่งคิวเก่าข้าม Organization

### 9.2 Confirmation ที่จำเป็น

ใช้ confirmation กับยกเลิกงาน นำช่างออก reset Join Link และเขียนทับพิกัด ส่วน action ที่แก้ไขกลับได้ง่ายเช่น filter และเปิดเครื่องไม่ต้อง confirm ทุกครั้ง Confirmation ต้องบอกชื่อ object และผลกระทบ ปุ่มหลักใช้คำกระทำจริง

### 10.2 Accessibility

• สถานะมีข้อความและไอคอนประกอบสี สีตัวอักษรปกติต้องผ่าน contrast เป้าหมาย 4.5:1 และ large text 3:1 ก่อน release

• รองรับ text scaling ของ iOS และ Android ขยายได้โดยไม่ตัดปุ่มหรือข้อมูลสำคัญ

• ลำดับ screen reader สอดคล้องกับ visual order ปุ่ม icon only มี accessible label

• Focus หลังเปลี่ยนหน้าตั้งที่ heading error focus ไป field ที่ผิด และ success ประกาศเพียงครั้งเดียว

• Touch target อย่างน้อย 44 dp ช่อง input รองรับ keyboard type ที่ถูกต้องและ autofill ตามบริบท

• เมนูเลือกและ dialog ทำ keyboard navigation ได้ ไม่ใช้ hover เป็นทางเดียว

• ภาพประกอบมีคำอธิบาย ภาพบริการจริงใช้ชื่อเครื่องและประเภทภาพแทน alt ที่เดาเนื้อหา

• ลด animation ตามระบบ ไม่ใช้ animation ยาวบังคับรอก่อนทำงาน

การตรวจ responsive ของต้นแบบผ่าน 320 และ 736 px ไม่แทนการตรวจ dynamic type screen reader native keyboard และ contrast ของทุก component ต้องมีการทดสอบอุปกรณ์จริงก่อน release

### 10.3 Native mobile behavior

Respect safe areas, status bar และ gesture zone ปุ่มหลักไม่ถูก keyboard บัง เมื่อออกจากฟอร์มที่มีข้อมูลและยังไม่เก็บ draft ให้แจ้งรักษาข้อมูล ใช้ back behavior เดียวกันตาม platform ถ่ายรูปกลับฟอร์มเดิมไม่สร้าง state ใหม่ซ้ำ

Location permission ขอเมื่อกดปุ่มแยก กล้องขอเมื่อกดถ่าย Notifications ขอหลังเห็นประโยชน์ เช่นรับงานแรก ไม่ขอ permission ทุกตัวตอนเปิดครั้งแรก เมื่อ denied ให้คำแนะนำและทางเลือก ไม่วนขอซ้ำ

LINE OA Customer App รายงานเซ็นรับ Stock และ Billing ที่ร้านเรียกเก็บจากลูกค้าปลายทางไม่เพิ่มเมนูในแบบ MVP นี้ ส่วน Subscription ของแพลตฟอร์มและ Platform Console รวมในหัวข้อ 13 ถึง 18 จุดเชื่อม future LINE เป็นการนัดจาก service request ที่ Owner ยืนยัน ไม่สร้างงานโดยข้อความอัตโนมัติทันที

## 12 การส่งต่อพัฒนาและตรวจรับ

### 12.1 Screen contracts

| กลุ่ม | ข้อมูลเข้า | ผลที่ต้องเกิด |
| --- | --- | --- |
| Onboarding | verified identity หรือ shop join token | Organization หรือ JoinRequest ที่มี state ถูกต้อง |
| Customer Location | organization membership และ contact | Customer Location ในร้านเดียวกัน ไม่สร้างซ้ำจาก retry |
| Job | customer location schedule assignment | แผนงานที่ช่างมีสิทธิ์เห็นและ inbox notification |
| Actual Service | job equipment media และผู้บันทึก | ServiceEvent และผลรายเครื่องแยกจากแผน |
| Maintenance | actual service date และ equipment interval | due record ที่เปลี่ยนเมื่อบริการจริง |
| Search and Media | authenticated scope และ query | ข้อมูลและรูปเฉพาะที่มีสิทธิ์ |
| Member management | owner role และ membership target | อนุมัติ ระงับ reset หรือ remove พร้อม audit |

Frontend ไม่เชื่อ organization_id จาก form เพียงอย่างเดียว Backend ตรวจ membership และ object scope ทุก endpoint Media ต้อง private และตรวจสิทธิ์ URL ที่หมดอายุ OCR asynchronous ไม่อยู่ใน transaction ที่ขวาง complete Notification เป็น side effect ที่ retry ได้

### 12.2 Checklist เกณฑ์ยอมรับ

• Owner สร้างร้าน และช่างหลายคนใช้ Join Link ชุดเดียวได้ pending ไม่เห็นข้อมูล

• รับงานได้แม้ไม่มี GPS Equipment Model Serial และ installation history

• Customer มีหลายสถานที่ Job และ Equipment อยู่สถานที่ที่สอดคล้องกัน

• หน้าเริ่มและเสร็จไม่อ่าน GPS ภาพไม่เก็บ GPS EXIF โดยเงียบ ๆ

• OCR success และ failure มีทางไปต่อ ผลภายหลังไม่ทับค่าที่ตรวจแล้ว

• หลายเครื่องมี actual result และรอบต่างกันได้ ไม่สร้าง history ให้เครื่องที่ไม่ได้ทำ

• Ad hoc ใช้บริบทเดิมได้และไม่ต้องรอร้านสร้างงาน

• Complete และ retry ไม่สร้าง ServiceEvent หรือ Schedule ซ้ำ

• Maintenance นำไปนัดโดย reuse และไม่ reset รอบก่อนบริการจริง

• ช่างใหม่เห็นข้อมูล ภาพ ประวัติ และพิกัดสถานที่เดิม

• Suspended removed และ ID ของร้านอื่นถูกปฏิเสธทั้ง data media search notification

• ฟอร์มย้อนกลับไม่หาย keyboard ไม่บัง action และผ่าน a11y ก่อน release

### 12.3 สิ่งที่ตรวจแล้วในต้นแบบ

ทดสอบ Owner registration → OTP จำลอง → ร้านพร้อมใช้ Technician Join → pending → approve จำลอง ลูกค้าใหม่ → สถานที่ไม่มี GPS → นัด → review → งานใหม่ Technician service → รูปจำลอง → รอบ → complete และ Maintenance → rebook → confirm ผลไม่พบ JavaScript runtime error และไม่พบ horizontal overflow ใน 50 render states ที่ความกว้าง 320 และ 736 px

ตรวจ appearance แบบ light และ dark ในหน้าตัวอย่าง การตรวจนี้ไม่ใช่การทดสอบ SMS กล้อง GPS offline sync push authorization database หรือ screen reader จริง ภาพโทรและแผนที่เป็น simulation ไม่มีการติดต่อผู้ใช้จริง

### 12.4 งาน engineering ที่ยังต้องทำ

• ยืนยัน auth recovery session lifetime และ technician identity ที่กู้เครื่องได้

• ต่อ QR และ share sheet เข้ากับ Join Link ที่ออกโดย server พร้อมปิดและ reset ที่ตรวจสิทธิ์จริง

• ต่อ API และ state machine status membership assignment และ actual service

• แทน illustration ด้วย media จริง พร้อม crop thumbnail upload และ metadata policy

• เพิ่มเลือกวันกำหนดรอบเอง รองรับรายการเครื่องที่เปลี่ยนได้ ไม่ใช้ข้อมูลคงที่จาก prototype

• ทำ per equipment draft รูป หมายเหตุ type และ selection ให้ persist ตลอด flow

• ทำ idempotency optimistic concurrency conflict และ audit รวมทั้งการแก้ completed

• ระบุขอบเขต offline และสิทธิ์ช่างค้นลูกค้าก่อน production

• ทดสอบ accessibility contrast dynamic type locale ไทย และอุปกรณ์จริง

• ทดสอบ with shops ว่าการบันทึกทั่วไปเข้าเป้าประมาณหนึ่งนาทีและใช้ซ้ำง่าย

### 12.5 งานรอบถัดไปที่เสนอ

### 14.1 Owner flow

สมาชิกของร้าน → เลือกแพ็กเกจ → ตรวจยอด วันมีผล และรอบ → เลือกช่องทาง → ส่งหลักฐานหรือ hosted checkout → pending → เงินยืนยันแล้ว → แสดงรอบใหม่ ข้อความ success ของการส่งหลักฐานต้องใช้ ส่งหลักฐานแล้ว แทน ชำระสำเร็จ

หน้าราคาแสดงสกุลเงิน รอบก่อนจ่าย ภาษีหรือการรวมภาษีตามข้อมูลที่ยืนยัน และวันที่แพ็กเกจใหม่มีผล ไม่ใช้ราคาต่อเดือนของรายปีโดยไม่บอกยอดชำระจริงรวมรายปี Upgrade downgrade แสดงผลต่อ seats storage OCR และรอบเดิมก่อนตกลง

การหยุดต่ออายุแสดงใช้งานถึงวันที่ใดและสิ่งที่จะเปลี่ยนเมื่อหมดรอบ พร้อมกดยกเลิกการหยุดก่อนวันสิ้นสุดได้ ไม่มีข้อความที่ทำให้เข้าใจว่าได้เงินคืนโดยอัตโนมัติ Owner เปลี่ยนคนได้โดยสมาชิกยังเป็นของร้าน

### 14.2 Console flows

ร้านทั้งหมด → รายละเอียด → subscription usage team → action ที่มี permission → กรอกเหตุผล → preview ผลกระทบ → step up หรือ approval ตามประเภท → confirm → server result → audit การนำทางทุกหน้าระบุร้านเป้าหมายชัดเจนเพื่อป้องกันแก้ผิดร้าน

รับเงิน: pending queue → invoice proof reference → ตรวจยอดกับเงินรับจริง → approve หรือขอหลักฐานใหม่ → result → period ใหม่และเอกสาร โดยปุ่ม approve disabled ระหว่างส่งและต้อง refresh หากอีกคนตรวจไปแล้ว

Support: ticket → ข้อมูลเทคนิคที่ masked → ขอ scope เฉพาะ target → pending consent และ approval → access active มีเวลาเหลือ → อ่านแบบ read onlyพร้อม audit → หมดอายุหรือ revoke แล้วปิดข้อมูล การอ่านสำเร็จไม่แปลว่าได้สิทธิ์แก้ในนาม Owner

หน้าผู้ดูแลใช้ข้อความก่อนและหลังการกระทำที่ต่างกัน เช่น ส่งคำขอคืนเงิน กับ ยืนยันคืนเงินจริงแล้ว ทุก high impact action ต้องใส่เหตุผล อ่านสรุป target และผลก่อนกด ในหน้าร้านหมดอายุไม่ใช้สีแดงเหมือนละเมิดความปลอดภัย

### 15.1 การเข้าถึงและความปลอดภัยใน UX

คง label และ focus ของ field มี validation ใต้ field role alert และ status หลังส่ง ใช้สีร่วมกับข้อความ Provider hosted form และ MFA ต้องใช้งานคีย์บอร์ดได้ เอกสาร export และ support attachment มี private access ไม่แสดง token หรือ bank secrets ในหน้าหรือ error

MFA recovery ผู้ดูแลต้องมี flow แยกจากร้าน บัญชี disabled ออกจากระบบได้ทันทีเมื่อ server ปฏิเสธคำขอ การยืนยันซ้ำไม่ทำให้ข้อมูลฟอร์มหาย ใช้ pending approval state ที่อ่านได้แทนซ่อนคำสั่งหลังบันทึก
